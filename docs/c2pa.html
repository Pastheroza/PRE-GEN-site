PRE-GEN inside C2PA

PRE-GEN v5 · v5 bundle: pg.proof.v1 (assertion label org.pregen.proof) · earlier assertion: pg.assertion.v1 · not yet tested end to end with a platform

Version 5. The proof extension carries the whole signed record in a C2PA manifest: for every subject of the job, the request, the registry's answer, the provider's report naming the output's SHA-256 (and soft bindings that survive re-encoding), and the registry's acknowledgement. When metadata was stripped, a platform fetches the registry's part by the report id. A platform checks it as of the moment the output was made, and against the file. The rest of this page describes the earlier assertion, which stays valid.

C2PA answers “who made this and when”. It does not answer “were they allowed to”. PRE-GEN adds that answer as a signed record inside the C2PA manifest, so the permission travels with the file instead of living in a database somewhere.

Division of labor C2PA says where a file came from. PRE-GEN says whether it was permitted. The record is not a licence; it points to one, and anyone can look up the PG codes and check the signatures against the registry's public keys, without trusting the file's author.

What goes into the assertion

The registry signs pg.assertion.v1 only for an allowed decision that already has the provider’s receipt, so the assertion and the receipt always name the same output (PRE-GEN-EXTENSIONS.md X.7). Every member is always present. The signed bytes are the canonical JSON of the object without signature and signing_key_id: 

{
  "schema_version": "pg.assertion.v1",
  "assertion_id": "assert_…",
  "decision_id": "dec_…",
  "subject_id": "PG-000042*",
  "license_id": "PG-PRM-…",
  "provider_id": "prov_studio_one",
  "model_id": "image-model-2",
  "decision": "allow",
  "purpose": "commercial",
  "rules_snapshot_hash": "9c1e…",
  "output_hash": "4f2a…",
  "issued_at": "2026-10-17T09:30:00+00:00",
  "signature": "a3f1…",
  "signing_key_id": "pg-ed25519:…"
}
FieldMeaning
decision_idThe allowed decision the assertion is bound to
subject_idThe subject, as the decision named it — resolvable at /lookup
license_idThe licence the decision resolved against; null when the allow needed none
decisionAlways allow: only an allowed decision can have a receipt
purposeThe intended use the decision answered
rules_snapshot_hashThe hash of the exact rule inputs that produced the decision
output_hashThe output’s SHA-256, from the receipt
signature, signing_key_idThe registry operator key’s signature and its key id; not part of the signed bytes

Getting it and embedding it

After filing the receipt, the provider asks the registry for the assertion. Asking again returns the byte-identical original, never a re-signed copy: 

POST https://api2.prampta.com/v1/assertions/
Authorization: Bearer $PROVIDER_SECRET
X-Provider-ID: your-provider-id
X-Licensee-ID: lic-…

{"decision_id": "dec_…"}

Anyone can fetch an issued assertion with GET /v1/assertions/{decision_id}. The registry produces only this statement; building and signing the C2PA manifest is the provider’s job, with any C2PA-conformant SDK. Where the statement goes in the manifest is not specified.

The PRE-GEN assertion never replaces the C2PA signature — it sits alongside it. Stripping the assertion breaks the studio’s chain-of-title check; stripping the C2PA signature invalidates the manifest. Both tamper paths are visible.

Verification, from anywhere

  1. Read the manifest and find the assertion where the provider placed it.
  2. Take the key named by signing_key_id from the registry’s key set (GET /keys), and only if the signed directory lists it for that registry.
  3. Verify signature over the canonical JSON of the assertion without signature and signing_key_id.
  4. Compare output_hash with the file’s SHA-256; a re-encoded file no longer matches.
  5. Optionally, a party with an account at the registry fetches the evidence bundle (GET /v1/audit/evidence/{decision_id}) and walks the audit chain back to genesis.

The signature check needs no account and no SDK: the file carries everything needed to ask “was this authorized?” and check the answer cryptographically.

What this is not

An assertion is evidence, not permission. The permission is the license; the assertion proves which license applied and that the provider asked. It also says nothing about provenance of the input material — that remains C2PA’s job. The two layers are complementary by design: C2PA for origin, PRE-GEN for consent.
