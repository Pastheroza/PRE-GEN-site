Protocol overview

PRE-GEN v5 · 12 October 2026 · Copyright Valerii Egorov · Apache-2.0 · the core · source · The text is normative; the JSON Schemas and byte vectors test it, and a disagreement is an erratum.

PRE-GEN is a protocol for pre-generation authorization. Before a generative system produces an output that uses a protected subject — a person's likeness or voice — it asks the registry that speaks for the subject. The registry answers and signs the answer. Anyone can check that answer later, offline, without trusting whoever shows it.

The core, in five rules

The whole core fits on one page: PRE-GEN-CORE.md. A provider that does exactly this, and nothing more, implements PRE-GEN.

  1. A code names the subject and its registry. PG-<prefix>-<number><check>, for example PG-TEST-000001N. The four-letter prefix names the registry. Codes without a prefix were issued before v5; they keep their meaning, and no registry issues new ones.
  2. The directory says whom to trust. One directory, signed by the steward key, lists each registry's prefix and keys. A verifier accepts a registry's signature only for its own prefix, and loads the directory again at least every 24 hours.
  3. Ask. POST {api}/v2/requests with one pg.request.v1 about one subject: subject_ref, provider_id, profile, use, job_id, job_hash. The prompt and the output never leave the provider.
  4. A signed answer. allow, deny, review or not_blocked, signed by the registry, bound to the exact request, valid for at most 900 seconds. Only allow permits.
  5. Generate only on a valid allow, and keep it. Every subject of the job needs a valid allow. The kept answers are the provider's proof.

Messages

envelope       = { type, body, signatures }      body.signers = [{ role, key_id }, …]
signing input  = "PREGEN-V5" 0x00 type 0x00 canonical(body)      → Ed25519 (RFC 8032), hex
message id     = SHA-256("PREGEN-V5-ID" 0x00 type 0x00 canonical(body))   signatures not included
key id         = "pg-ed25519:" + hex(SHA-256(raw public key))[0:32]
canonical      = UTF-8, keys in code-point order, no whitespace, integers only, no normalization

Never Unicode-normalize a signed body before verifying. Verify the bytes you received.

Extensions — optional, and they only add

ExtensionSolves
reportsWhat happened: a report signed by the provider, an acknowledgement signed by the registry
provider-keysProvider signing keys: first key, rotation, recovery
limitsLicences with a number of uses: reserve, count, give back
jobsOne generation with several subjects; with the provider's job rules, never generating twice
grantsLicences as signed objects (pg.grant.v1)
licenseeAnswers for a connected end user
observeTrial mode: ask and record without blocking
sandboxThe same eight test subjects in every sandbox, and a test directory
lookupPublic lookup of a code
identityOne person in several registries: who proved it, not who came first
proofThe signed record travels with the output; platforms check it
catalogSubjects who chose to be offered; resale only with an explicit right

No extension may turn a refusal the core or a profile requires into a permission. A client sends members of an extension only to a registry that declares it.

The profile likeness/1

likeness/1 says what use contains for a person's likeness and voice, and which refusals nothing overrides: an opt-out, an unavailable subject, a minor's likeness in a prohibited category, an immutable denial, and an intimate category without the person's own signature.

One person, several registries

A claim the person confirmed on their own official channel silences unconfirmed claims. A refusal of the person in any of their registries holds in all of them. Several unconfirmed claims freeze: nobody permits until someone proves it. A registry answers a complaint within seven days, and the steward can mark a false claim in the directory. See identity.

No intermediary required

A provider and a registry exchange requests and answers directly, free. Services that make this easier — checking a representative's authority, running a sale, reporting, settlement — are optional, and anyone may offer them.

The earlier interface

pg.decision.v1, POST /v1/verify/, licences pg.license.v2 and receipts stay valid and verifiable for everything issued under them, and get no new features. Their text, and the foundations the core builds on, are in PRE-GEN-SPEC.md; the origin registry's additions are in PRE-GEN-EXTENSIONS.md.

Conformance

JSON Schemas for every v5 message are in spec/schemas; byte vectors in messages.json and vectors.json. The vectors use fixed public test keys — never use them in a deployment. An open reference registry and the verification libraries are described under Implement.
