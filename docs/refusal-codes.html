Refusal codes

Version 5: the core and likeness/1 · earlier interface: 38 codes, 17 core and 21 of PRAMPTA's own · policy version 2026-09-22

Version 5

A “no” is a signed answer with a reason, not an HTTP error. The core defines two reasons, the profile likeness/1 the rest, and a registry may add its own. A reason you do not know is still a no.

Core, for every registry and profile:

  • PG_UNKNOWN_SUBJECT — the registry holds no such subject, so it has no decision to give. Not a prohibition, and not a permission.
  • PG_OTHER_REGISTRY — the code's prefix belongs to another registry.

Protections of likeness/1, checked before any licence; no licence, extension or registry policy overrides them:

  • PG_SUBJECT_OPTED_OUT — an opt-out in effect.
  • PG_SUBJECT_UNAVAILABLE — the subject is pending, paused or withdrawn.
  • PG_PROHIBITED_USE — a fixed protection forbids the use: a minor's likeness in a sexualised or otherwise prohibited category.
  • PG_IMMUTABLE_DENIAL — an immutable denial.
  • PG_PERSONAL_SIGNATURE_REQUIRED — an intimate category (sexual, adult) without the person's own signature.

Other reasons of likeness/1:

  • PG_NO_LICENSE — no grant covers this licensee and use.
  • PG_USAGE_LIMIT — the grant's uses are spent.
  • PG_SUBJECT_DISPUTED — a complaint about this code is being examined. Refused at this registry only: it is not a refusal of the person in other registries.
  • PG_SCOPE_VIOLATION — outside the grant's scope.
  • PG_REVIEW_REQUIRED — held for a human; comes with status review.
  • PG_NOT_CONNECTED — this use needs a connected end user; show it as “connect your account”, not as a refusal.

Extensions:

  • PG_PROVIDER_NOT_ACCEPTED — the registry has not vetted this provider, known only by its domain, and answers it only about published subjects (their refusals included) and its own connected licensees (provider-identity). A refusal; it hides whether a private code exists, and a private subject's own refusals.
  • PG_NOT_BOUND — HTTP 403: the licensee has not connected their licences to this app; show it as “connect your licence” (bind).

PG_IDENTITY_UNCONFIRMED is an outcome of the client's own check of a public person (identity), not a registry answer.

Errors about the request itself are HTTP errors with {"error", "error_description"}: PG_MALFORMED (422, the request does not follow the core), PG_NOT_AUTHENTICATED (401, credential, signature or provider_id not accepted), PG_PROFILE_UNSUPPORTED (422, the registry does not answer under this profile).

Earlier interface (/v1)

Core codes are used by every registry with this meaning (spec §3). The rest are PRAMPTA’s own, defined before v5 without a prefix and kept for compatibility; new codes of every registry, PRAMPTA included, carry its issuer prefix, PG_<ISSUER>_….

Every decision from POST /v1/verify/ carries a reason. A hard code means no retry, reshaped request or new licence changes the answer. A soft code means a different request, a valid licence or a different provider might succeed. An unknown code must be treated as hard.

Two codes are not refusals: PG_STD_TRACKING_ONLY comes with not_blocked (personal use, nothing granted) and PG_ORG_INTERNAL_USE with allow.
