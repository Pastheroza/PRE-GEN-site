Versions

PRE-GEN v5, 12 October 2026 — the current version · PDF · VERSIONS.md. The PDF is kept as published; the text on pregen.org supersedes it (no watermark, TOG- codes).

Specification versions

PRE-GEN has one version number, the same here, in the specification source and on Zenodo. Each version is one Zenodo release under the concept DOI 10.5281/zenodo.20129901. Until the v5 record is published there, that DOI resolves to v4 (2026-06-01), which v5 supersedes. The current text is this site and the v5 PDF.

  • A version is a published snapshot. The number changes only with a new release, here and on Zenodo. Changes made in between wait for the next one.
  • Nothing issued ever changes meaning. A code or signed answer valid under one version stays valid under every later one. A version may stop issuing something, never stop recognizing it.
  • Each version lists what changed against the previous one — see VERSIONS.md for v4 → v5.
  • Drafts for the next version are informative only, not part of v5. Authorized Releases: releases with the artist's permission, and stamping AI content that already exists.

v5 message types

The v5 interface names each message by its type, and the type is part of the signed bytes, so a signature over one kind of message can never be replayed as another: pg.request.v1, pg.answer.v1, pg.report.v1, pg.report_ack.v1, pg.keyset.v1, pg.grant.v1, pg.anchors.v1, pg.access.v1 (provider-identity), pg.bind_exchange.v1 and pg.binding.v1 (bind), pg.terms.v1 (terms), and the bundle pg.proof.v1. JSON Schemas for each are in spec/schemas. The markers below belong to the earlier interface, which stays valid.

Signed object markers (earlier interface)

Updated 2026-10-17 · Independent of the specification version

Every signed object carries its schema version inside the signed bytes — the version marker is itself cryptographically committed, not a label on the envelope. This page states, for each object: what the marker is, what bumps it, and which changes are additive-safe.

The compatibility rule Adding a new optional field does not bump a version: every SDK already ignores unknown fields and defaults missing ones, so additive changes are free. Removing a field, changing a field’s meaning, or changing what a value can mean — that is a new version.

Decision vs policy versioning

The schema (schema_version) is the shape of the envelope; the policy (policy_version) is the rule set that filled it in. They are stamped independently. A decision can be read against exactly the rules in force when it was signed, even after the rules change — both versions are on the object. Policy history is append-only: every entry names the date and the change, and every PG_* refusal code is registered and classified there (see Refusal codes).

Why some objects are deliberately not additive-safe

The license body’s v marker was added as a hard cut: the point was a real, load-bearing version marker inside the signed bytes, not another optional field a legacy row can silently ignore. The identity assertion’s audience string is part of what gets signed — changing it is exactly how a v2 assertion refuses to replay against a v1 verifier. Where a break is possible, it is a break on purpose, so a signature from one format era cannot silently pass as another.

Receipts: a fixed shape

Every member of a receipt is always present, so any change of shape is a new marker (pg.receipt.v3 was added that way, to sign the event type). A registry may accept a provider signature over the current or the previous shape during an announced window, signalled with Deprecation and Sunset headers (PRE-GEN-SPEC.md §6.1, §7). pg.receipt.v2 and pg.receipt.v3 coexist today with no sunset date.
